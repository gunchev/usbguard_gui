## Executive summary

All items from `REVIEW-2026-08-28.md` have been addressed: the HID
lock/unlock race is fixed (`_on_list_devices_result` now gates on
`self._screensaver.active`), `USBGuardClient.connect()` stops the previous
worker thread before starting a new one (no more leaked `_DBusThread`s, and
the exponential backoff in `_try_connect()` is now reachable and tested),
"Allow (Temporary)" no longer deletes permanent rules, disconnected/lock-
unavailable state now disables dialog and device-list actions with a warning,
`NameOwnerChanged` gives proactive daemon-loss detection, `stop()` uses a
bounded wait + `terminate()` fallback, "Close" is the default dialog button,
the screensaver slots were renamed, and the doc/polkit-rule drift items were
corrected. Tests: 203 passed, ruff clean, pyright clean (0 errors), autopep8
clean, coverage 81%.

This pass found **one new real bug** (a resource leak in the device dialog)
and **three new robustness gaps**, all previously unflagged. No new security
regressions in the HID/lock flow were found — the fixes from the last review
hold up under closer reading and match their tests.

## 🔴 Real bugs

### 1. `DeviceActionDialog` leaks itself for the life of the app

`src/usbguard_gui/device_dialog.py:106` + `src/usbguard_gui/app.py:445-456`

```python
if self._screensaver is not None:
    self._screensaver.connection_changed.connect(lambda _available: self._update_actions_enabled())
```

Every `DeviceActionDialog` connects a lambda to `ScreensaverMonitor
.connection_changed` — a signal on the single long-lived `ScreensaverMonitor`
instance owned by `USBGuardTrayApp`. PyQt only auto-disconnects a connection
when the *slot itself* is a bound method of a QObject; here the slot is a
plain lambda, so PyQt has no way to know it closes over a QObject (`self`,
the dialog) and never disconnects it. Nothing else disconnects it either:
`_show_device_dialog()`'s `on_finished` callback (app.py:448-453) only pops
the dialog from `self._open_dialogs` and calls nothing on the dialog itself,
and neither `DeviceActionDialog` nor its caller ever sets
`Qt.WidgetAttribute.WA_DeleteOnClose` or calls `deleteLater()`.

Effect: every USB device insertion that opens a prompt dialog (any device
while unlocked, or HID with "special treatment" disabled) permanently leaks
that dialog object — held alive forever by the connection on `_screensaver`
— and each subsequent `connection_changed` emission (screen-lock service
connects/disconnects) calls `_update_actions_enabled()` on every dialog ever
opened, including long-closed ones. On a machine with frequent hot-plugging
(docking stations, test benches) this grows unbounded for the lifetime of
the tray process (which is designed to run for weeks, per the SIGUSR1
self-restart feature).

**Fix:** disconnect explicitly on close (e.g. in a `closeEvent`/`finished`
handler call `self._screensaver.connection_changed.disconnect(self
._update_actions_enabled)` using a bound-method connection instead of a
lambda so PyQt can also auto-disconnect it), and/or set
`WA_DeleteOnClose` on the dialog so Qt actually destroys it once closed.

## 🟠 Robustness gaps

### 2. Overlapping unlock cycles can silently drop the "devices connected while away" prompt

`src/usbguard_gui/app.py:209-223` (`_on_list_devices_result`) +
`app.py:411-419` (`_on_screensaver_unlocked`)

`_screensaver_pending_ids` is a single overwritable slot, not a per-request
queue:

```python
def _on_screensaver_unlocked(self, active: bool) -> None:
    if active or not self._screensaver_pending_devices:
        return
    self._screensaver_pending_ids = list(self._screensaver_pending_devices)
    self._screensaver_pending_devices.clear()
    self._client.list_devices()
```

Repro:
1. Screen locked, device A inserted → deferred (`_screensaver_pending_devices={A}`).
2. Screen unlocks → `_screensaver_pending_ids=[A]`, `list_devices()` fired (R1 in flight).
3. Before R1 returns, the screen locks again and device B is inserted while locked → `_screensaver_pending_devices={B}`.
4. Screen unlocks again → `_screensaver_pending_ids=[B]` **overwrites** `[A]`, a second `list_devices()` fires (R2 in flight).
5. R1 arrives first (FIFO) → consumes the *current* `_screensaver_pending_ids`, which is now `[B]`, not `[A]` → filters R1's (stale) device snapshot for B, likely finds nothing → **A's summary/dialog never appears**, and `_screensaver_pending_ids` is set back to `None`.
6. R2 arrives → `_screensaver_pending_ids is not None` is now **False** → R2's result is dropped entirely too → **B's summary/dialog never appears either**.

Both devices stay blocked (fail-safe, not a security issue) but the user is
never prompted for either and has no indication anything is pending —
they'd have to notice via the device list window. Same class of bug as the
already-fixed "duplicate event delivery on reconnect" (`REVIEW-2026-08-28.md` #2): a
single mutable slot standing in for what should be per-request state.

**Fix:** correlate each `list_devices()` call with the pending-id set it was
issued for (e.g. a small queue, or piggyback a request id / use
`functools.partial`/closures per call instead of one shared field), or debit
`_screensaver_pending_devices` against the ids actually satisfied instead of
overwriting.

### 3. Business-logic D-Bus errors are treated the same as a lost connection

`src/usbguard_gui/dbus_client.py:233-277` (`_do_apply_policy`,
`_do_list_rules`, `_do_remove_rule`)

```python
async def _do_apply_policy(self, device_id: int, target: DeviceTarget, permanent: bool) -> None:
    try:
        rule_id = await self._devices_iface.call_apply_device_policy(device_id, int(target), permanent)
        ...
    except DBusError as e:
        if _is_permission_error(e):
            ...
        else:
            ...
            self._set_connected(False)
```

Any non-permission `DBusError` — including ordinary, expected failures like
applying a policy to a device that was unplugged a moment earlier (the same
race already covered by `TestHIDLockOnDeviceRemoval` for the HID path, but
not guarded here) — is treated as a lost daemon connection: `_set_connected
(False)` fires, the tray tooltip flips to "disconnected (retrying...)", and
`USBGuardTrayApp._on_connection_changed` schedules a full reconnect, which
tears down and rebuilds the entire `_DBusThread` (new `MessageBus`, new
signal subscriptions) even though the daemon and bus connection were never
actually broken. Since `apply_device_policy()` is fire-and-forget (no
result signal reaches the dialog/list window, by design per `DESIGN.md`),
the user also gets no direct feedback about *why* the app suddenly shows
"disconnected" right after clicking Allow/Block on a device that happened to
be removed first.

**Fix:** only flip `_connected` on errors that actually indicate a broken
transport/session (e.g. `DBusError` types like `NoReply`,
`ServiceUnknown`/`NameHasNoOwner`, or catching `EOFError`/`OSError` from the
socket) rather than on any non-permission `DBusError`; log and swallow
business-logic errors (bad device id, unknown rule id) without touching
connection state.

### 4. Screensaver/session D-Bus loss is only detected reactively, unlike the (already fixed) USBGuard daemon watch

`src/usbguard_gui/screensaver.py:92-155`

`dbus_client.py` now watches `NameOwnerChanged` for `org.usbguard1` so a
daemon crash/restart is detected proactively (`REVIEW-2026-08-28.md` #5, already
fixed). `screensaver.py`'s `_ScreensaverThread` has no equivalent watch for
`org.freedesktop.ScreenSaver` (or the session bus itself) after the initial
connect — once `_main()` gets past the connect-retry loop, the only way
`ScreensaverMonitor.connected` (i.e. "lock availability", which gates *all*
allow/deny actions per the `_actions_enabled()` security contract) becomes
`False` again is if a later `lock()` or `GetActive` call happens to fail.
If the screen-locker service exits or crashes after the app connected (KDE
lock-screen crash/restart, session bus hiccup, etc.), `_lock_available`
stays stale `True` until the next HID insertion actually tries to lock —
at which point the "New keyboard/HID attached… Locking screen…" warning has
already fired, the lock attempt fails, and only then does the app learn
locking is unavailable and mark the device blocked-and-abandoned (fail-safe,
not insecure, but confusing: the user was told a lock was coming that never
happens, followed by a second "screen locking unavailable" notice).

**Fix:** subscribe to `NameOwnerChanged` for `org.freedesktop.ScreenSaver`
on the session bus (mirroring `dbus_client.py`'s pattern) so loss is
detected immediately instead of on the next lock attempt.

## 🟡 Minor / cosmetic

5. **`open()` without explicit encoding** (from the untracked `AUDIT.md`,
   still unresolved): `_get_introspection()` in both `dbus_client.py:56` and
   `screensaver.py:48` does `with open(path) as f:` — relies on the
   platform/locale default encoding for bundled UTF-8/ASCII XML. Add
   `encoding="utf-8"`.
6. **Dead code:** `Device.vendor_id` / `Device.product_id`
   (`device.py:118-126`) are still unused outside their own test
   (`tests/test_device.py::test_vendor_product_id`); `USBGuardClient
   .remove_rule()` / `_DBusThread._do_remove_rule()` are fully implemented
   and tested but no longer called from any application code path now that
   "Allow (Temporary)" doesn't remove rules (`REVIEW-2026-08-28.md` #3) — either wire
   it up somewhere (e.g. a "Remove rule" action in the device list) or drop
   it.
7. **`QLockFile` lifetime is implicit:** `app.py:510` — `_lock` is a local
   variable in `main()`, kept alive only because `app.exec()` blocks in the
   same stack frame. Works today, but there's no explicit `.unlock()` in
   `_quit()` and nothing stops a future refactor (e.g. extracting `main()`'s
   body into a helper) from releasing the lock early. Consider storing it on
   `QApplication` or module scope, as `AUDIT.md` already noted.
8. **Duplicated `_get_introspection` + thread boilerplate:** `dbus_client.py`
   and `screensaver.py` still each define their own `_get_introspection`
   helper and near-identical `_schedule`/`stop()`/bounded-wait patterns
   (`AUDIT.md` recommendation #5, not yet done). Not a bug, just a
   maintenance/DRY opportunity if a third D-Bus subsystem is ever added.

## Suggested priority order

1. Fix the `DeviceActionDialog` leak (#1) — it's an unbounded resource leak
   in a long-running background process.
2. Fix the `_screensaver_pending_ids` overwrite race (#2) — silently drops
   user-facing device prompts.
3. Narrow the connection-drop trigger in `_do_apply_policy` /
   `_do_list_rules` / `_do_remove_rule` (#3) — avoid spurious full
   reconnects on ordinary per-call errors.
4. Add `NameOwnerChanged` watching for the screensaver service (#4) for
   parity with the daemon-loss fix already shipped.
5. Sweep the minor items (#5-#8) opportunistically.
