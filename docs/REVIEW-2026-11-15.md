defect and two high-severity gaps in the HID contract itself. The critical one sits beneath

## Assumptions

Everything below rests on these. Where one is wrong, the findings that cite it change.

**Decided by the maintainer during this review (2026-11-15):**

- **A1. A deliberate click is enough.** A manual Allow on a HID device needs no screen lock; the
  click itself shows a person is at the machine. The lock-first rule governs *automatic* and
  *held* allows only. (Shapes finding 7.)
- **A2. The planted-device attack is in scope.** An attacker who plugs a keystroke injector into
  an unattended machine and waits for the owner to unlock is someone the app should defend
  against. (Makes finding 2 High.)
- **A3. KDE Plasma plus the listed desktops are 1.0 targets** — GNOME, LXQt, XFCE. (Makes
  finding 3 a release blocker rather than a note.)
- **A4. The KVM/dock rule-placement fix has not been confirmed on real hardware.** (Carried
  forward.)

**Assumed by the reviewer, not confirmed:**

- **A5. The attacker is a physical device, not local code.** The shipped polkit rule lets any
  process in an active local session call `applyDevicePolicy` directly, so the app's gates are
  guards on its own UI, not a boundary against malware already running as the user.
  **Confirmed by the maintainer, 2026-11-16.**
- **A6. USBGuard 1.1.4 behaves as its source reads.** Three facts were taken from the upstream
  source at tag `usbguard-1.1.4`, not observed on a live daemon:
  `Utility::escapeString` escapes only `"`, `\` and non-printable bytes, so braces and spaces in
  a device name pass through; `RulePrivate::toString` writes `name` before `with-interface`; a
  non-permanent `applyDevicePolicy` uses a default-constructed rule whose id is
  `Rule::DefaultID` (`UINT32_MAX`), and the implicit rule's id is `UINT32_MAX - 1`.
- **A7. `ImplicitPolicyTarget=block`** and the daemon's default `authorized_default` handling,
  as the README already assumes: an inserted device arrives blocked and
  `DevicePresenceChanged` fires *before* policy is applied.
- **A8. No test hardware was used.** Nothing here was checked against a real device, a real
  screen locker, a real polkit agent or an installed RPM.
- **A9. Not verified at all:** how KDE reports `GetActive` during its unlock grace period;
  what GNOME's `org.freedesktop.ScreenSaver` implements; whether KDE's notification server
  renders markup in message bodies; whether the daemon rejects a group/world-readable
  `rules.conf`; which interpreters the CI matrix really runs (no access to CI logs).

## Findings

### 1. A device's name or serial can forge the interface list the app parses — Critical

`parse_device_rule()` (`device.py:487-510`) does not tokenise the rule. Each field is pulled out
by an unanchored regex over the whole string (`_extract_field`, `device.py:171-183`;
`_extract_interfaces`, `device.py:186-196`), so text *inside a quoted value* is matched like
syntax. The daemon writes `name` before `with-interface` and leaves braces unescaped (A6), so a
device controls what `with_interface` — and therefore `has_hid_interface()`
(`device.py:122-128`) — returns. Both directions were reproduced.

**A non-HID device posing as HID is authorised with no interaction.**

```
block id 0525:a4a2 name "USB Ethernet with-interface { 03:01:01 }" … with-interface { 02:06:00 0a:00:00 }
```

parses as `with_interface == ['03:01:01']`. Plugged into a **locked** machine it takes the
"HID inserted while locked" branch (`decision.py:495-502`) and the engine issues
`ALLOW`/`UNCHANGED` at once. On an unlocked machine it is allowed five seconds later, behind the
lock. Either way a network adapter or storage device is live without any prompt — USBGuard's
protection is bypassed for an arbitrary device class on an unattended machine.

**A keyboard posing as storage loses every HID protection.**

```
block id 1234:5678 name "SanDisk Ultra with-interface { 08:06:50 }" … with-interface { 03:01:01 08:06:50 }
```

parses as `['08:06:50']`. The engine emits an ordinary prompt instead of the lock flow, the
dialog shows *Type: Mass Storage*, and Allow stays enabled even with locking unavailable. One
click on what looks like a flash drive puts a keyboard on an unlocked session. A single-interface
keyboard needs only `with-interface 08:06:50` in its name.

The same root cause corrupts other fields. A rule that carries `parent-hash` but no `hash`
yields `hash == <the parent hash>` (the `hash` pattern matches inside `parent-hash`), which
feeds the permanent-allow cache and `rule_identity()`; a value ending in `id ` or `hash ` makes
the next field swallow the text between two quotes.

The tokenizer that gets this right is already in the same file: `parse_rule_predicates()`
(`device.py:244-280`) returns the true interface list for both strings above.

**Fix:** build `parse_device_rule()` on `parse_rule_predicates()` so quoting is honoured, and
drop the regex extractors. Add tests with hostile names and serials — none existed. The earlier
trust-boundary work (`rule_persistence_problem`) guards what is *written*; nothing guarded what
is *read*.

**Fixed 2026-11-15.** `parse_device_rule()` now reads the rule's tokens; `_extract_field`,
`_extract_interfaces` and their regexes are gone. Anything the tokens do not state plainly stays
empty instead of being guessed: a rule that does not tokenise yields no fields, a single-valued
field given several values stays empty, `with-interface` under an explicit set operator stays
empty, and a repeated attribute keeps its first value. Empty is the safe direction — a device
with no readable interfaces is never auto-allowed, and a rule with no readable identity is never
claimed as a device's own. One behaviour change follows from that: a permanent rule whose `if`
condition does not tokenise is no longer treated as a device's own rule, so `Once` and `Always`
leave it alone.

**Hardened 2026-11-15.** A stray or unterminated quote now makes the rule unreadable too. The
tokenizer used to take such a quote as a bare word, so a crafted malformed rule could still forge
the interface list; a device name cannot reach that path because the daemon escapes quotes and
backslashes, but the "unparseable yields nothing" invariant now holds without that caveat.

Tests: `TestParseDeviceRuleReadsTokensNotText` (`tests/test_device.py`) and
`TestForgedInterfaceList` (`tests/test_decision_engine.py`) — 25 cases, 19 of which fail against
the old parser. Gate: 678 passed, lint and pyright clean. Not tested against a live daemon or a
real device (A8).

### 2. A HID device auto-allowed behind the lock stays allowed after unlock — High

Both automatic paths — inserted while locked (`decision.py:495-502`), and the lock flow's
allow (`decision.py:252-261`, safety net at `196-217`) — apply a temporary allow that lasts
until unplug. Nothing re-checks it at unlock, and the unlock summary lists only *non-HID*
deferred devices (`decision.py:242-250`). The only trace is a five-second tray notice shown
before the screen locked.

So the attack A2 puts in scope works: plant an injector on an unattended machine, the app
allows it behind the lock, the owner returns and unlocks with their own keyboard, and the
injector is live on the unlocked session. The README says the flow "prevents an unattended
unlocked machine from being hijacked"; that holds only until the next unlock. Step 3 there
("you must enter your password with the newly-attached device") is not enforced and cannot be —
the app cannot tell which keyboard typed the password.

**Options, weakest to strongest:**

- Tell the owner at unlock which HID devices were activated while away. Cheap, and consistent
  with the existing summary, but an injector that is already live can dismiss a notice.
- Prompt at unlock with *Keep / Block* per device. The same caveat applies to any prompt a live
  keyboard can answer.
- Re-block every auto-allowed HID device at unlock and ask before re-allowing. This is the only
  variant that closes the attack. Its cost is real: the owner of a single, non-permanent
  keyboard would need a mouse to confirm, so it has to exempt or special-case that situation.

This is a design decision for the maintainer; the review's recommendation is the third option
with a mouse-operable confirmation, and the first as the minimum.

### 3. "Screensaver active" is treated as "password required" — High, unverified

Every lock decision reads `org.freedesktop.ScreenSaver` `GetActive` / `ActiveChanged`
(`screensaver.py:113`, `212-216`). That signal means *the screensaver is active*, which is not
the same as *a password is needed*:

- **KDE Plasma** has an "allow unlocking without password for N seconds" grace period after an
  idle lock. If `GetActive` is true during it, a device plugged in then is allowed immediately
  and its own first keystroke dismisses the locker.
- **Desktops with a lock-less screensaver** (blanking without lock, or lock-after-delay) report
  active while any key press returns to the session.
- **GNOME, Cinnamon, MATE and Xfce** are now reached through their own services (the locker
  registry on `master`). All four descend from gnome-screensaver and, as far as the reviewer
  knows, share its settings: locking can be switched off, and a lock delay lets the screen blank
  first and lock later. In both cases the locker reports active while any key press returns to
  the session. A HID device plugged in then takes the "inserted while locked" branch and is
  allowed at once.

The registry answers *reachability* only. Its integration tests
(`tests/test_screensaver_integration.py`) run against stub services written from the documented
API, so they prove names, paths and `Lock()` signatures, not what a real locker's "active" means.
The README's locker table (light-locker, xscreensaver under the freedesktop name) is likewise
unverified.

None of this was tested on a real desktop (A9). With A3 making these desktops 1.0 targets, each needs a live
check before release. A desktop-neutral source worth evaluating is logind's session
`LockedHint`, with `Session.Lock` for locking.

### 4. Tray app aborts when the prompt times out under its own warning box — Medium

`DeviceActionDialog._action_blocked()` raises `QMessageBox.warning(self, …)`
(`device_dialog.py:239`, `246`) — a modal box parented to the dialog, running a nested event
loop. The 30-second countdown keeps ticking inside that loop (`_tick`, `device_dialog.py:202-207`),
closes the dialog, and `_on_finished_cleanup` calls `deleteLater()`. The dialog is destroyed
while the message box it owns is still executing.

Reproduced: daemon disconnected, click any action, leave the warning open until the countdown
ends, then dismiss it — the process dies with `double free or corruption`, exit 134. The
warning text invites exactly that wait ("try again once the connection is restored"). After the
abort nothing restarts the tray app, so prompts and the lock flow are gone until the next login;
devices stay blocked.

**Fix:** stop the countdown while the warning is up, or show the warning without a parent/nested
loop (a non-modal box, or an inline label in the dialog).

### 5. A known keyboard on a different port gets no reaction at all — Medium

`_permanent_allow_hashes` is keyed on the device hash alone (`decision.py:188-194`), but the
rules the app writes — and those `usbguard generate-policy` writes — pin `via-port` and
`parent-hash`. A permanently allowed keyboard moved to another port arrives blocked, its hash is
in the cache, and `on_device_inserted` returns silently (`decision.py:503-507`): no lock flow, no
prompt, no notice. Reproduced. The user's own keyboard is dead until they open the device list or
lock the screen and replug. It fails safe, and it is exactly the KVM/dock case the app cares
about.

The same cache has three smaller defects: it ignores rule order, so a `block` rule above the
`allow` changes nothing; it is wiped when a rules read fails (finding 10); and it is empty until
the first `list_rules` answer lands (the startup race from the 2026-09-28 review, still present).

The cache exists only to suppress the "New keyboard/HID attached" notice for devices the daemon
is about to allow by itself. **Fix:** keep the ruleset and ask `rule_matches_device()` in rule
order, as the device list already does (`device_list.py:80-103`), treating an undecidable rule as
"not known".

### 6. A keyboard plugged in while locked is not allowed if an inhibitor is held — Medium

`_hid_lock_flow_applies()` (`decision.py:314-326`) requires `not inhibited`, and the
locked-screen allow sits inside that condition. With the screen locked and a logind idle
inhibitor held, a newly attached keyboard is treated as non-HID and deferred until unlock
(`decision.py:533-537`) — which that keyboard was needed for. Reproduced.

The inhibitor check exists because the app will not lock against the user's wish. When the
screen is *already* locked there is nothing to lock and the password gate is in place, so the
check has no purpose there. A user returning to a locked machine through a KVM during a package
transaction is locked out unless the keyboard has a permanent rule.

**Fix:** test `screensaver.active` before the inhibitor, so the anti-lockout branch depends only
on the screen being locked.

The current behaviour is pinned as intended by
`test_hid_insert_while_locked_and_inhibited_prompts` (`tests/test_decision_engine.py`), so this
is a contract change for the maintainer to accept, not a regression to patch.

### 7. The lock-unavailable gate contradicts the "a click is enough" contract — Medium

With locking available, a manual Allow on a HID device is applied immediately on an unlocked
session — from the device list at any time, from the prompt while an inhibitor is held. With
locking unavailable the same click is refused (`gate.py:51-59`), and the stated reason is that
the app "cannot lock first". It never locks first on a manual click.

Under A1 the gate therefore blocks a legitimate action for no security gain, and on a session
with no locker it forces the user to switch the whole HID treatment off to allow a keyboard.
Three texts state a stronger rule than the code implements:

- `AGENTS.md`: "may only be allowed while the screen is locked";
- `README.md`, *When Screen Locking Is Not Possible*: "allowing a keyboard without being able
  to lock first would hand an attacker an unlocked session";
- `device_dialog.py:119-128`, the `_allow_enabled` docstring, says the same.

**Fix:** either drop the gate for manual clicks, or keep it and document it as deliberate
friction. In both cases restate the invariant as what is enforced: *no automatic and no held
allow of a HID device outside the lock.* The automatic paths already refuse to run without a
working lock, so removing the click gate opens nothing new.

### 8. Device-supplied strings are rendered as rich text — Medium

The prompt builds `QLabel(self.device.name)` and the same for serial, port and connection
(`device_dialog.py:141-150`). `QLabel` defaults to auto-detected rich text; a name containing
markup is rendered as HTML (reproduced: `textFormat()` is `AutoText` and Qt classifies the
string as rich). A device can add lines, emphasis and links to the security prompt — for
instance a fake second "Type:" row.

Tray notices carry the name too (`app.py:450-455`, `decision.py:182-183`). Whether the desktop
renders markup there was not verified (A9).

**Fix:** `setTextFormat(Qt.TextFormat.PlainText)` on every label holding device data, and
HTML-escape device strings in notification bodies.

### 9. Overlapping refreshes can leave the device list empty — Low

`DeviceListWindow` pairs two untagged signals with one boolean (`device_list.py:258-291`). If a
second refresh starts before the first one's rules answer arrives, that answer renders the
just-cleared `_pending_devices`, clears `_refresh_pending`, and the second devices answer is
then discarded. Reproduced: the table stays empty until the next event. The window is narrow —
two refreshes within one round trip, e.g. the refresh after a decision followed by the
debounced one. The unlock cycles had this problem and solved it with request ids.

### 10. A failed rules read is reported as an empty ruleset — High (raised from Low 2026-11-16)

`_do_list_rules` emits `[]` on error and `list_rules()` does the same when disconnected
(`dbus_client.py:824-833`, `895-900`). The device list then shows every device as **Temporary**
— a confident wrong answer in a column that exists to say *Unknown* when it cannot tell — and
the engine's permanent-allow cache is cleared. Reproduced. `list_devices_result` was given a
`None`-means-failed contract for this reason; the rules signal was not.

**Raised to High 2026-11-16 (maintainer):** the unlock-quarantine design (handover §3b/§3c)
makes the ruleset load-bearing security state — the engine consults it in rule order before
the HID flow, and a matching permanent block rule suppresses the auto-allow. A failed read
reported as an empty list therefore silently erases every permanent-block suppression and
lets the app auto-allow a permanently blocked device behind the lock. The display nit above
is unchanged; the severity is for the suppression bypass. It is now a prerequisite of the
finding-2 fix.

### 11. "Permanent" detection depends on an integer wrap — Low

`on_device_allowed` treats `rule_id > 0` as "allowed by a permanent rule" (`decision.py:439`).
The daemon sends `UINT32_MAX` for a temporary allow (A6), which is greater than zero. The check
works only because the id crosses `pyqtSignal(int)` — a 32-bit signed C int — and arrives as
`-1` (reproduced on PyQt 6.11). Declare the signal differently, or have a future PyQt raise on
overflow, and every temporary allow would poison the cache or drop the signal. The tests model a
temporary rule as `rule_id == 0`, a value the daemon never sends. Compare against the sentinel
ids explicitly.

### 12. The SIGUSR1 restart is deferred, and fails in the first 30 s — Low

- The handler (`app.py:532-538`) is a Python signal handler, which runs only when the main
  thread next executes Python. Under an idle Qt loop that is the next device event or tray
  click (reproduced: a signal sent at 1.0 s was handled at 3.8 s, when the next Python slot
  ran). After a package update the old code keeps running until then, and an event that triggers
  the restart is processed by a process about to replace itself.
- `os.execv` runs with the instance `QLockFile` still on disk. In the first 30 seconds of
  uptime the new image sees a fresh lock owned by its own pid, reports "Another instance is
  already running" and exits (reproduced; after 30 s the lock counts as stale and the restart
  works).

**Fix:** wake the loop with `signal.set_wakeup_fd` or a socket notifier, and unlock before
`execv`.

### 13. Several failures reach only the log — Low

- A live apply that fails on an `Always` decision for any reason other than device bring-up —
  a polkit denial, a device id that went stale in the list — is logged and nothing is shown
  (`dbus_client.py:571-598`). `Once` reports the same failure through `temporary_apply_failed`.
- `apply_device_policy()` returns silently when disconnected (`dbus_client.py:880-886`). The
  lock flow has already emptied its pending set by then (`decision.py:258-261`), so that
  keyboard stays blocked with no retry.
- Coroutines are scheduled with no done-callback (`dbus_common.py:62-64`); an unexpected
  exception surfaces as asyncio's "exception was never retrieved" at best.

### 14. A rolled-back rule is restored at the end, not where it was — Low

`_restore_permanent_rule` re-appends at `_APPEND_RULE_AT_END` (`dbus_client.py:805-822`). If the
removed rule sat above a broader one, the restored copy now sits below it and may be shadowed,
while the log says "Restored". Passing the id of the rule that preceded it would keep the order.

### 15. No cap on prompts for a device that changes identity — Low

The cooldown and the dialog dedup are keyed on identity, which includes the serial. A device
that re-enumerates with a new serial each time gets a new always-on-top dialog and a new notice
every time, and `_last_prompted_at` grows without bound. The pending maps are capped at 32; open
dialogs and the cooldown map are not.

### 18. One failed `Lock()` leaves locking marked unavailable for the session — Medium

Found on `master`. `_do_lock` reports "unavailable" on any `DBusError`, and now also when
`Lock()` takes longer than `_CALL_TIMEOUT` (5 s). Nothing ever probes again: `GetActive` is
re-read only when the locker's bus name changes owner, and `lock_for_pending_hid` will not call
`Lock()` while locking is marked unavailable. Reproduced: one failed `Lock()` emits
`connected(False)` and no re-probe follows. From then until the locker or the app restarts, the
lock-first flow is off and every HID Allow is refused — after a single transient error, or a
lock that merely took six seconds and then succeeded.

Two smaller points in the same code: the locker is chosen once at startup and never re-probed
if a different one from the registry appears later; and `_do_lock` handles only `DBusError` and
timeout, so any other exception leaves the app believing the lock was requested.

**Fix:** after a failed `Lock()`, re-probe `GetActive` on a timer and restore availability when
it answers.

### 16. Packaging and CI — Low

- `%preun` runs `systemctl disable --now usbguard-dbus.service` on removal, even if the admin
  enabled it for another client.
- `%post` appends `generate-policy` output to `rules.conf`; if the file does not exist it is
  created with the scriptlet's umask, not `0600` (effect on the daemon not verified, A9).
- Dev and lint tools are unpinned and no `uv.lock` is tracked, so the gate is not reproducible
  and a new linter release can break CI unprompted.
- `skip_missing_interpreters = true` lets a Python version drop out of the matrix silently.
  (`master` has since moved the matrix to Fedora 44/45 and added Python 3.15; the setting is
  unchanged as far as this review knows.)
- `RPM_VER` comes from the newest tag, so an RPM built from an untagged tree carries the last
  release's version.

### 17. Documentation drift — Low

- "Reject" is still described as offered: the RPM `%description`, the `pyproject.toml`
  description, the `AGENTS.md` overview, and the user-facing strings "Block and Reject still
  work" (`ui_strings.py`, `decision.py:296-297`). The UI has offered no Reject since the action
  set.
- README *Architecture* omits `decision.py`, `gate.py` and `ui_strings.py`.
- README *Generic install* points at `dist/usbguard_gui*.desktop'` (stray quote; the files are in
  `rpm/`). Typos: "Uppon", "Manu bugs".
- `AGENTS.md` still tells agents to use Graft (*Read this first* #3, the docs table, checklist
  step 6) while its new section and the working tree use Trail.
- Stale comments: `screensaver.py:316-321` and the log line at `347` say all allow/deny
  functionality is disabled; `dbus_client.py:1011-1017` says the GUI never removes rules;
  `dbus_client.py:148-149` is a comment about introspection sitting above an unrelated function;
  `device_list.py:373` and `TODO.md` name `_rule_identity` / `_RULE_IDENTITY_ATTRS`, both renamed.
- `DESIGN.md` says signals are connected in the facade's `__init__` (it is `connect()`) and that
  callers follow an apply with `list_rules()` (none does).

## What is solid

- **The engine boundary.** `DecisionEngine` touches no widgets and speaks through four signals;
  `gate.py` is the one place a click is judged. `decision.py` is at 100% coverage.
- **Fail-closed defaults.** Close, Escape and timeout apply nothing; Enter dismisses; a held
  Allow never authorises a HID device; a failed lock leaves devices blocked.
- **The durable-write path.** One lock serialises every permanent mutation; remove-then-append
  rolls back; partial clears are reported as partial; `reject` cannot be persisted;
  device-reported rules are validated before being written.
- **Honest failure reporting** on the paths that have it — five distinct notices that say what
  did and did not change.
- **Lock-state hygiene.** Owner generations and revision counters stop a departed locker's
  answer, or a stale query, from authorising anything.
- **Bounded state** for unlock cycles and held decisions.
- **The polkit exposure is documented plainly**, with the tightening shown inline.
