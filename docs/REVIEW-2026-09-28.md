## Executive summary

No exploitable defect found in the HID lock-first contract. The failure directions are
deliberate and almost all point at *blocked*: no lock service disables every action, an
idle inhibitor drops the auto-allow, a permanent write that only landed temporarily is
told to the user instead of buried in a log, and a device-reported rule is validated
before it can become `/etc/usbguard/rules.conf`.

**Nothing this app does can lock you out persistently — but not for the reason first written
here.** The only permanent write reachable from the UI is `Allow (Permanent)`; Block and
Reject are `permanent=False` at every call site (`device_dialog.py:193,200`,
`device_list.py:261-262`). That does **not** mean a block dies at the next reboot — it means
the opposite. A blocked device comes back **blocked**, because blocking is not an overlay this
app applies: it is USBGuard's floor. `ImplicitPolicyTarget=block` (confirmed live on the
author's machine) blocks every device with no matching allow rule, and that floor is
re-established on every boot whether or not anyone ever pressed Block.

So the persistent layer is the **allow list**, and on that layer the app is one-way: it can
add and replace allow rules but never delete one, so it cannot persist a denial worse than the
default. On the *live* layer it moves devices freely in both directions — Block an allowed
device, Allow a blocked one — but a live Block does not outrank a permanent Allow across a
reboot, and that asymmetry is its own problem: see #12. Recovery is real, but the mechanism
is a **fresh decision opportunity**, not cleared state — see #3.

The interesting findings are **not** security holes. They cluster around two principles
this app has to respect, only one of which is written down anywhere:

- **The user must never be locked out of their own machine.**
- **A device the honest user can restore with their own hands is a good trade.**

The first makes item #1 load-bearing and untested. The second is why two earlier findings —
*warn before disabling the last HID*, and *change the Reject default* — are retracted below:
Reject is recoverable by unplugging and replugging, so the disconnect **is** the recovery
rather than the harm. What survives is narrower and cheaper than what was written first.

## The lockout principle

While the screen is locked, a HID device has exactly one thing it can do: **type into the
lock screen**. The compositor grabs input, so the device can unlock the session or trigger
lock-screen actions (sleep / power off) — nothing else. It cannot touch the desktop, a
terminal, or any application.

That inverts the usual reading of "auto-allowed with no user confirmation":

- The **password prompt is the confirmation gate**. An attacker who plugs a keyboard into a
  locked machine still has to know the password. Allowing the device does not widen the
  attack surface; the lock is what was already gating it.
- The **alternative is total lockout**. If the user's built-in keyboard is blocked, broken,
  or on the other side of a KVM switch, the newly attached device is the *only* way back
  into the workstation. Refusing to allow it does not make the machine safer — it makes it
  unreachable, and the recovery is a power cycle or a console login.

So `app.py:355-361` (HID inserted while the screen is already locked → temporary allow)
is correct, and it is load-bearing in a way the other branches are not. Every other
auto-allow path protects the user *from* a device; this one protects the user's *access*.

This is worth writing down explicitly, because the natural instinct when reviewing an
unconfirmed `apply_device_policy(ALLOW)` is to gate it. See the retraction below.

## The three layers, and where "block" actually lives

This review got the persistence story wrong on a first pass, so it is worth pinning down
before anything else here is read:

| Layer | Where it lives | Survives reboot? | Who can write it |
|---|---|---|---|
| **Allow list** | `/etc/usbguard/rules.conf` | **Yes** | The app — `Allow (Permanent)` only |
| **Default floor** | `ImplicitPolicyTarget=block` in `usbguard-daemon.conf` | **Yes** — it *is* the default | The admin; never the app |
| **Live target** | the daemon's in-memory state for a connected device | No | The app, for the current session |

`Block` and `Reject` sit in the third layer, which is why every call site passes
`permanent=False`. But the second layer means that third-layer block and a first-layer
*absence of an allow* are indistinguishable from the user's point of view: **the device does
not work.** So "not persistent" must not be read as "self-correcting". Nothing self-corrects.
The floor is permanent by construction, and the only way off it is an explicit allow rule.

Two different claims follow from that table and must not be conflated:

- **Live layer (3): the app moves devices freely in both directions.** Block an allowed
  device, Allow a blocked one — that works, immediately, every time.
- **Persistent layer (1): the app is one-way.** It can add an allow rule, and it can replace
  one allow rule with another, but no UI path deletes one. `remove_rule()` is implemented on
  the client and wired to nothing outside `_persist_device_rule`'s own replace step.

For the lockout question: the app cannot make the *persistent* situation worse than a fresh
install, because it has no lever that digs deeper than the default floor. That is why the
lockout analysis keeps coming out recoverable — not because blocks fade, but because blocks
are never dug in at all.

What it also means, and this is the part that bites: **persistence is asymmetric between
Allow and Block.** `Allow (Permanent)` survives a reboot; `Block` does not. See #12.

## 🟠 Availability gaps

### 1. The anti-lockout branch is the only auto-allow path with no test

`src/usbguard_gui/app.py:355-361` — HID inserted while `screensaver.active` is true,
allowed temporarily with no prompt — is **never exercised** by the suite. Coverage lists
356-361 as missed.

This matters more than a typical coverage gap, and for the opposite reason to how it was
first written up. A regression here does not open a hole; it **locks the user out**. If
somebody adds a guard above this branch, reorders the checks, or "tightens" the condition,
the failure is silent and the user discovers it at the worst possible moment: locked out,
no working keyboard, no error message.

Every neighbouring path has a regression test — including ones that genuinely regressed
before (`TestHIDAllowRequiresLockedScreen` documents a real race where a keyboard was
allowed onto an unlocked session). This branch is the remaining hole, and it is the one
whose regression is *unrecoverable without physical intervention*.

Worth testing as three cases:

- HID INSERT while `active=True` → exactly one `apply_device_policy(id, ALLOW, permanent=False)`,
  no dialog, no lock timer started.
- The allow happens **before** the `_permanent_allow_hashes` check, so an empty cache
  (daemon just started, `list_rules` not yet returned) cannot cause a lockout.
- The allow is temporary — a permanent allow here would outlive the login and is not what
  the contract promises.

### 2. Hardwired HID is the one device you cannot replug

The lockout argument that survives is narrow, and it is not about the last keyboard — it is
about the last keyboard **you cannot physically unplug**.

Reject is recoverable by design: unplug, replug, the device re-enumerates, USBGuard sees an
unknown device again, and the user gets a fresh prompt. That covers external keyboards,
mice, docks, KVM legs, and Bluetooth (power-cycle the keyboard). The fail-safe direction is
correct and the recovery is a physical action the honest user can always perform.

What replug does not cover is `with-connect-type "hardwired"` — the internal laptop keyboard.
Rejecting that disconnects something the user cannot unplug, so the recovery step grows from
"replug" to "reboot". It is still **fully recoverable** (#3), so this is friction rather
than a lockout — worth being precise about, because the guard below is a nicety and not a
necessity.

The signal is already there and completely unused. `Device.with_connect_type` is parsed
(`device.py:69`, mapped at `device.py:213`), displayed in the dialog
(`device_dialog.py:63`) and in the device list (`device_list.py:120`) — but **no decision
anywhere reads it**. A guard scoped to `with_connect_type == "hardwired"` **and**
`has_hid_interface()` is a few lines against data the app already holds, and it replaces the
broad TODO item with something that fires only when the recovery step happens to be the
annoying one.

That is a better-targeted version of *"Warn when an action would disable the last
keyboard/mouse HID"* — which, for anything repluggable, is warning about a problem that does
not exist.

### 3. The recovery ladder is real, and undocumented

Every lockout this app can produce is recoverable — but the mechanism needs to be stated
precisely, because it is **not** that a block expires. It never does. Blocking is USBGuard's
default floor (`ImplicitPolicyTarget=block`), so a device with no allow rule is blocked on
every boot and stays blocked until someone explicitly allows it. Pressing Block does not make
the blockage persistent; the blockage was already there, and the button just applies it now
instead of at the next boot.

What recovery actually means is that you get **another chance to decide**, and that chance
arrives at several points:

1. **Replug.** The device re-enumerates as unknown and the app prompts again, which reopens
   the decision. The device is blocked the moment it lands — the fresh prompt is the recovery,
   not a cleared state. Covers anything removable.
2. **Reboot.** `rules.conf` is re-read from scratch and the device is blocked again — and then
   the locked-screen auto-allow branch (#1) lets you log in with a newly attached HID device,
   or the app prompts and you allow it explicitly. The block survives; your way back survives
   with it.
3. **The pre-USBGuard window.** USBGuard is a systemd service that activates long after the
   keyboard is usable. GRUB, the kernel and the initramfs all have a working keyboard before
   `usbguard.service` starts — including the LUKS passphrase prompt, which is precisely the
   case where a keyboard *must* work regardless of what USB policy says. Interrupt at GRUB
   (`init=/bin/bash`, `systemd.unit=rescue.target`, or the distro's recovery entry) and the
   daemon never comes up at all: rescue and single-user do not pull in `multi-user.target`, so
   `usbguard.service` stays down and `rules.conf` can be edited at leisure.
4. **SSH from another machine.** `usbguard list-devices` plus an edit to
   `/etc/usbguard/rules.conf` (or `usbguard append-rule`) recovers without a reboot, and is
   the only rung that needs no keyboard at the locked machine.
5. **Boot other media.** Mount the root filesystem from a live USB and edit `rules.conf`, or
   `systemctl disable usbguard`. The universal fallback; it does not care what the policy did.

None of this is in the README. The escape hatches are all real; the one thing that would stop
a user panicking — writing them down — has not been done. A short "If you lock yourself out"
section costs nothing and changes the feel of every other decision in the app, because the
fail-safe stops looking terminal. For a tool whose default answer is "the device stays
blocked", saying how to unblock it is part of making that default livable.

**One caveat worth recording.** The *API* can write a permanent block —
`apply_device_policy(..., target=BLOCK, permanent=True)` is a valid call and `_persist_device_rule`
would happily append it. No UI path makes that call today: every Block and Reject in
`device_dialog.py` and `device_list.py` passes `permanent=False`. So "you cannot lock yourself
out persistently" is a property of the **call sites**, not of the API. If someone later adds a
"Block permanently" menu item, this analysis needs revisiting — worth a comment at those call
sites so it does not get added casually.

The same asymmetry cuts the other way and is worth knowing: the one persistent change the app
can make that is *not* an allow is in `_persist_device_rule`, which removes the device's
existing rule before appending the replacement (`dbus_client.py:462`). If the append fails and
`_restore_permanent_rule` also fails, a previously-permanent allow rule is lost. That is
logged loudly (`"could NOT be restored"`), it degrades to the pre-allow state rather than to a
block, and it recovers by rungs 1-2 above — but it is the only way this app can leave the
policy worse than it found it.

## 🟡 Minor / correctness

### 4. `is_hid()` is a footgun next to a security decision

`device.py:97-101` returns True only when **all** interfaces are HID. The security-correct
check is `has_hid_interface()` (`device.py:103-109`), which is what `app.py:344` uses.

`is_hid()` is public, fully tested, and used by **nothing but its own tests**. The name is
the problem: it reads like *the* HID check, and a contributor wiring it into a security
decision would silently exclude composite HID + mass-storage devices — precisely the
BadUSB class the README calls out by name. The docstring is honest, but nobody greps the
docstring before calling a method whose name already says what it does.

Delete it, or rename to `is_pure_hid()`. If it has no caller after that, delete it anyway.

### 5. Startup race on the permanent-allow cache

`list_rules()` fires on connect (`app.py:274`) and resolves asynchronously. Until
`_on_list_rules_result` populates `_permanent_allow_hashes`, a device that is already
permanently whitelisted is indistinguishable from a first-time device.

Consequence is bounded and fails safe: an already-allowed keyboard inserted while the
screen is *unlocked* in that window gets the full warning → lock → password dance instead
of being silently skipped. Annoying, not dangerous, and it never causes a lockout because
the locked-screen branch at 355 is checked *before* the cache lookup.

Note also that `_do_list_rules` emits `[]` on error, so a failed rules read leaves the
cache empty for the whole session — same fail-safe direction.

If it bites in practice, gate the HID *timer* (not the locked-screen allow) on the first
rules result having arrived.

### 6. README overstates the idle-inhibitor mechanism

README, *When Screen Locking Is Not Possible*: under a logind idle inhibitor
"the auto-allow-then-lock flow is skipped — **locking would be a no-op**".

An explicit `ScreenSaver.Lock()` generally still works past an *idle* inhibitor — that
inhibition class suppresses the *idle transition*, not a deliberate lock request. The
actual reason to back off is user intent: someone holding "Prevent screen lock" has asked
for the screen to stay up, and auto-locking against that is both surprising and unreliable.

The behaviour is correct and conservative. Only the stated rationale is stronger than the
mechanism, which matters because a future optimiser may read it, find the claim false, and
"fix" the check away. Suggest rewording to intent rather than capability.

## Second pass

Full read of `device_list.py`, `device_dialog.py`, `dbus_common.py` and the remaining
`dbus_client.py` / `app.py` surface, plus a claim-by-claim check of README and DESIGN against
code. `dbus_common.py` is clean — the bounded-stop / short-recycle-grace split is correct and
well argued. The findings below are new to this pass.

### 7. README advertises a hash column that does not exist

README, *Device List Window*: "Displays device name, ID, **hash** and class."

The actual columns (`device_list.py:19`) are:

```
#  Status  USB ID  Name  Serial  Port  Interfaces  Type  Connection
```

There is no hash column. `device.hash` is used internally — it is the join key for
`_permanent_allow_hashes` (`device_list.py:64,103`) — but it is never rendered. Fixed to
match the code. If a hash column is actually wanted, it is a one-line addition to
`COLUMNS` and `_display_data`; the value is already on the model.

### 8. DESIGN.md's signal table is missing `permanent_write_failed`

The `USBGuardClient Signals` table lists six signals. There are seven. `permanent_write_failed`
(`int, str, str`) exists on both the worker (`dbus_client.py:136`) and the facade
(`dbus_client.py:576`), is emitted at `dbus_client.py:329`, and drives a user-facing tray
notification — *"Permanent rule not saved … applies only until the device is unplugged"*
(`app.py:216`).

The prose compounds it: *"`apply_device_policy()` is fire-and-forget (no result signal)"*. That
was true before PR #8 and is now only half true — there is still no **success** signal, but
there is a **failure** one, and it is the most important signal on the class, because it is the
difference between a user believing they granted permanence and knowing they did not.

Both corrected. Anyone reading DESIGN.md to wire a new consumer would otherwise not know the
signal exists and would re-derive the notification badly or not at all.

### 9. The device list blanks to "no devices" on a transient D-Bus error

`_do_list_devices` swallows a `DBusError` and emits an **empty list** (`dbus_client.py:270-273`).
`DeviceListWindow._on_list_devices_result` cannot tell that from a genuine empty bus, so it
stores `[]`, fetches rules, and calls `set_devices([], …)` — the table clears.

So a momentary daemon hiccup while the window is open shows the user **no devices at all**,
which reads as "nothing is plugged in" rather than "could not refresh". The tray tooltip does
say *disconnected (retrying…)*, but the window — the thing they are looking at — lies by
omission.

What makes this worth fixing rather than shrugging at is that **the other path already learned
this lesson**. `_on_correlated_devices` treats an empty snapshot as a failure and puts the
cycle back, with a comment saying that dropping it "is how a transient disconnect silently lost
the prompt" (`app.py:500-507`). The untagged path that the device-list window uses never got
the same treatment. Same failure, two different answers.

The clean fix is at the signal level rather than in the window: distinguish *"empty"* from
*"failed"* — e.g. emit `None` instead of `[]` on error, or add a success flag — so every
consumer can tell them apart instead of each guessing. Fixing it in the window alone leaves the
next consumer to make the same mistake.

### 10. The lock-availability gate is wider than its own rationale

Both `DeviceListWindow._apply` (`device_list.py:287-300`) and `DeviceActionDialog._action_blocked`
(`device_dialog.py:165-172`) disable **every** action while `screensaver.connected` is False.
The stated reason is sound but specific:

> without the ability to lock first, **allowing** a keyboard would hand an attached-device
> attacker an unlocked session

That argument is about **Allow**. Block and Reject need no lock capability at all — they make
the situation strictly safer, and they are the two actions a user most wants when something
unexpected appears while the session is in a degraded state. As written, a ScreenSaver outage
means you cannot *deny* a suspicious device either; you can only watch it stay blocked by the
daemon's default policy and hope the locker comes back.

Not a safety bug — the direction is still "more blocked" — but it removes deliberate control
for a reason that does not apply to those actions. This is the same territory as the existing
1.0 item *"Lock-gate refinement: gate HID-capable devices only, and only while special HID
treatment is enabled and screen locking is unavailable"*, and the two should be resolved
together: gate `ALLOW` on lock availability, leave `BLOCK`/`REJECT` always available.

### 11. The dialog reports `Accepted` for Block and Reject

Verified empirically: `_on_block()` and `_on_close()` both call `self.accept()`, so
`QDialog.result()` is `1` (Accepted) for **every** button, including Reject.

Harmless today — every caller reads `result_target`, not the result code, and the
`QDialogButtonBox` `RejectRole` relay loses the ordering race because `_on_block` sets the
target and accepts first. But `result()` is now actively misleading: a future caller that keys
off the QDialog result code would read Reject as "user accepted". Either route through
`done()` with a distinct code per action, or leave it and say so in the class docstring so
nobody wires the wrong thing up.

## Third pass

### 12. `Block` does not survive a reboot, but a permanent `Allow` does

The asymmetry the three-layer table sets up — and it is a trap, not a safety property.

Take a device that already has a permanent allow rule in `rules.conf`. The user wants that
trust gone: the stick was seen somewhere untrustworthy, or it is leaving with someone. They
pick **Block**.

- **Live target:** blocked. The device stops working, the UI shows `Block`, the user is
  satisfied.
- **`rules.conf`:** untouched. `_apply()` passes `permanent=False`, so
  `call_apply_device_policy(id, BLOCK, False)` moves the live target and nothing else.
- **Next reboot:** the device matches the still-present `allow` rule and is **allowed again**,
  with no prompt and no reminder that anyone ever tried to revoke it.

The revocation was a pause, not a revocation, and nothing in the UI says so. Verified: no UI
path calls `remove_rule()` at all — it has no caller in `device_list.py`, `device_dialog.py`
or `app.py` — and `permanent=True` originates from exactly one place, `device_list.py:258`'s
*Allow (Permanent)*. There is no way to take permanent trust back from inside the app.

Why this matters more than it looks: the failure is **silent and security-shaped**. The user
performed the action that reads as revoking trust, got immediate visible confirmation, and the
revocation quietly evaporates at the next boot. It is the mirror image of the
`permanent_write_failed` case — there, the user thinks they granted permanence and did not;
here, the user thinks they removed permanence and did not.

**Resolution: make `Block` persistent too — including for HID — and warn instead of
forbidding.**

An earlier draft of this review argued the fix was to *not* offer a persistent Block, on the
grounds that it would break the "cannot lock yourself out" property. That was wrong, and the
carve-out it implied — no permanent deny for HID — would gut the feature exactly where it
matters most. Permanently blocking a keyboard is arguably the single most important thing
USBGuard exists for. A remotely-actuated or AI-driven HID device that must never be allowed on
a server is precisely the threat class, and the current app gives the admin no way to express
that decision at all.

Reframe the risk. It was never "HID is special" — it is **self-lockout**, and the app cannot
compute it:

- It can see which devices are allowed, and whether the target is `hardwired`.
- It **cannot** see IPMI / iLO / iDRAC / BMC / serial console / SSH, or a keyboard that is
  simply on the other side of a KVM and unplugged right now.

Any class-based or count-based prohibition will therefore be wrong for a real fraction of
deployments. A server that should only ever be driven over the network, with all local console
input permanently denied, is a legitimate and arguably *stronger* posture — and the "but it's
their only keyboard" heuristic would be wrong there.

So: **warn, confirm, allow. Never forbid.** The confirmation escalates with what the app can
actually see:

| What the app sees | Say it |
|---|---|
| Target is HID | "This permanently blocks a keyboard / input device." |
| `with_connect_type == "hardwired"` | "This device cannot be unplugged. After a reboot there is no way to undo this from the running system." |
| No other allowed HID would remain | "No other local input device would remain allowed." |
| Always | Name the recovery path: BMC/IPMI, serial console, GRUB single-user, live USB. |

The admin proceeds or does not. The app's job is to make the consequence legible, not to
overrule a decision it lacks the context to make.

**The implementation is nearly free.** `_RULE_IDENTITY_ATTRS` is
`("id", "serial", "hash", "parent_hash", "via_port")` — device and topology, **no target
verb**. So `_persist_device_rule` already treats a permanent `block` and a permanent `allow`
for the same device as one identity and *replaces* the old with the new, with dedup and
shadow-safe placement. Making Block permanent therefore delivers revocation for free, on code
paths already covered by `TestPermanentRuleDeduplication` and `TestPermanentRulePlacement`.

And the guard that protects hand-written policy is already in place: `_rule_identity()` returns
`None` for class rules that name no device — `allow with-interface { ... }`, or the
`reject with-interface all-of { 08:*:* 03:00:* }` rules in the author's own `rules.conf` — so
a tray decision can never clobber them. That is exactly the right boundary, and it means
permanent Block can be added without endangering existing admin-authored deny rules.

What still needs doing is the visibility piece: the dialog and the device-list menu must say
which of Allow/Block are permanent, and the escalating confirmation above has to exist before
permanent HID deny ships.

## Retracted

**Do not add `and self._lock_available` to the `_on_list_devices_result` safety net
(`app.py:248`).**

An earlier pass flagged that this site auto-allows pending HID devices on `screensaver.active`
alone, while the insert path additionally requires `lock_available`, and suggested making the
invariant uniform.

That advice is wrong and would introduce a lockout. The safety net exists to catch a missed
`active_changed` signal. If the ScreenSaver service is flaky or momentarily unreachable
(`lock_available == False`) while the screen genuinely *is* locked, gating on
`lock_available` would refuse the allow — and the user, keyboard just plugged in, screen
locked, would have no way back in.

Trusting `active` there is a deliberate availability-over-confidentiality trade, and it is
the right one: the residual risk is a stale `active=True` on a session that is actually
unlocked, which requires the ScreenSaver service to have died *while reporting locked* —
narrow, and far less severe than the lockout the gate would cause.

Leave it. If anything, document why the two sites differ, so the next reviewer does not
"fix" it again.

### ~~Warn before disabling the last HID / change the Reject default~~

Both dropped, on the recoverability argument.

Reject is not the harm — it is the recovery. Unplug, replug, the device comes back as
unknown and the user decides again. A device the honest user can restore with their own hands
is a strictly better trade than one that stays allowed and can inject keystrokes, which is
the entire reason the app exists. "One Enter from disconnecting your only keyboard" framed
the disconnect as the damage; it is the undo.

The residue is only the case where the replug is impossible, and that is finding #2 — a
`with_connect_type` check, not a change to the default button. The default stays.

### ~~No permanent Block for HID devices (class carve-out)~~

Retracted after the maintainer pointed out the obvious use case: a keyboard you must *never*
allow on a server — a remotely-actuated or AI-driven HID device — is exactly what permanent
deny is for. Carving HID out of permanent Block removes the capability precisely where the
threat model is strongest, and leaves the admin no in-app way to express the most important
decision available to them.

The mistake was treating a device *class* as a proxy for a risk that is really about
self-lockout — and self-lockout is not computable from inside the session, because the app
cannot see BMC/IPMI/serial/SSH. The correct response to an uncomputable risk is an escalating
warning and an explicit confirmation, not a prohibition that will be wrong for a meaningful
share of real deployments.

| Option | Verdict |
|---|---|
| **Block instead of Reject for the last HID** | Easier recovery than replug — the device stays enumerated and can be re-allowed with a mouse alone. Only worth it if Reject bites in practice; the replug path already covers the honest case, and Block is the weaker security answer. |
| **Trust-on-successful-unlock** — auto-allow a device that has unlocked N times | Redundant. **Allow (Permanent)** already expresses "I trust this keyboard", and it is granted rather than inferred. Inferred trust is strictly weaker than granted trust for no real UX gain. |
| **Grace window suppressing HID prompts after unlock** | Solves a case nobody has reported. The lock-first flow already leaves the device you just used allowed. |
| **Refuse to lock when zero HID would remain allowed** | Does not bite in the current flow: the device that triggered the lock is itself allowed by the time the lock lands, so at least one usable HID always exists. |
| **Rescue policy snapshot before any HID block** | Genuinely useful for sysadmins, but it is a feature rather than a fix. Post-1.0 if anyone asks. |
| **Port-pinning (allow only known ports)** | Strong, but it is a different product. USBGuard's rule language already does this; the tray GUI is the wrong layer for it. |
| **Mouse-only recovery** | Already true. A mouse is HID class `0x03` too, and the device list window is fully operable with one, so the real lockout is "zero HID **and** no SSH" — a documentation problem (#3), not a code one. |

The honest summary: the design is close to right. Most of what reads as a gap is already
closed by a physical action or by a menu entry that already exists. The residue is one
`with_connect_type` check and one README section.

## What is solid

Worth recording so it does not get eroded:

- **Composite devices are caught.** `app.py:344` uses `has_hid_interface()` (**any** HID
  interface), so HID + MSC BadUSB gets the lock-first treatment. This is the single most
  important line in the repo and it is right.
- **Fail-safe direction is consistent.** No lock service → all actions disabled. Inhibitor
  held → falls through to prompt, no auto-allow. Lock timer re-checks availability before
  firing and refuses to claim a lock that would not happen.
- **`rule_persistence_problem()`** refuses control characters, non-verb-leading strings,
  and anything carrying non-device directives before a device-reported string can become
  permanent policy — and falls back to the daemon's own upsert rather than dropping the
  user's decision.
- **Non-atomic permanent writes are handled.** Remove-then-append restores the removed rule
  on append failure, and a permanent write that only applied temporarily raises
  `permanent_write_failed` to a tray notification instead of a log line.
- **Bounded state.** Unlock cycles are capped at 32 (`MAX_PENDING_UNLOCK_CYCLES`) and
  correlated per-call, so a daemon that stays down cannot grow the map for the life of the
  process, and the device-list window can no longer consume an unlock cycle.
- **Repo hygiene.** `.env` untracked, generated `graft/` ignored, no bare excepts, no
  TODO/FIXME left in `src/`, constants match the README (5 s HID delay, 30 s dialog
  timeout).
- **The polkit exposure is documented loudly.** The shipped rule grants passwordless USB
  control to every active local user; the README says so in a section titled for it, shows
  the `wheel` tightening inline, and tracks the open/strict subpackage split for 1.0. This
  is the largest real-world exposure in the project and it is handled about as well as it
  can be short of shipping the strict default.
